# スコアランキング: CPU 計測記録と投稿頻度見積り

スコアランキング機能(`POST /api/scores` のサーバー側リプレイ検証)の CPU コストを、
実装計画のタスク1(Free 枠判定)とタスク6(完全実行の再計測)で計測した記録。
**タスク7の停止ポイントで Paid / Free を判断するための材料**としてここに残す。

生データは [`docs/measurements/`](./measurements/) に置いてある(後述)。

---

## 1. 結論(先に要点)

| 判定 | 結果 |
| --- | --- |
| Free 枠(10ms CPU/リクエスト)で成立するか | **不成立(確定)** |
| タスク6の判定式 `p99(A) + max(p99(B-success), p99(B-rejected)) ≤ 1,000ms` | **FAIL(2,887ms)** |
| Paid 枠で成立するか | **成立する見込み**(下記「Paid の読み方」参照) |

タスク6の 1,000ms 判定は**不合格**である。ただしこれは
「Paid でも成立しない」という意味ではない — 判定に使った数値が
**ローカル wall-clock の代理値**であり、Paid の課金・制限単位である
**実 CPU 時間ではない**ためである(§4 参照)。

---

## 2. タスク1: Free 枠判定(実施済み・確定事実)

実 Cloudflare 上に一時 Worker をデプロイして計測した。

- フィクスチャA: **p99 = 366ms**
- フィクスチャB-success: **p99 = 477ms**
- 多数のリクエストが **10ms の CPU 上限で強制終了(`exceededCpu`)** した

この計測で確定したのは **「Free 枠の 10ms/リクエストでは成立しない」ことのみ**。
打ち切りを含む計測なので「完全実行なら何 ms か」は未確定であり、
**合算値 843ms を完全実行時間として扱ってはならない**(実装依頼書の明示要件)。

→ **CPU ゲート不合格(Free 前提)を正式記録する。**

---

## 3. タスク6: 完全実行の再計測

ローカル workerd(`wrangler pages dev`)の CPU 上限を拡張し、
**打ち切りなしで全リクエストを完走**させて再計測した。

### 3.1 実行環境

| 項目 | 値 |
| --- | --- |
| マシン | Apple M1 / 8 コア |
| Node.js | v20.19.5 |
| wrangler | 3.114.17(ローカル workerd / Miniflare) |
| 実行形態 | `wrangler pages dev` に対する**直列**(並列なし)リクエスト |
| 計測値 | **クライアント側 wall-clock**(下記の注意を参照) |

### 3.2 方法論(タスク1と同一)

- 各系列について**ウォームアップ 10 リクエストを捨て、続く 100 リクエストを計測**
- p99 は昇順ソートの **99 番目(nearest-rank 法)**
- クレームは**本番と同じ `Game.update()` 経由**で発生させる(field 直接書き換えでバイパスしない)
- **RLE 検証・展開からレスポンス生成まで、本番 POST と同じ経路**を通す

### 3.3 フィクスチャ

| 系列 | 内容 | 結果 |
| --- | --- | --- |
| **A**(敵最大負荷) | ステージ10相当の敵数上限(Wisp 10・Ember 最大10)・10800 tick 完走 | 200 / accepted |
| **B-success**(クレーム最大負荷) | 敵オブジェクトは最大数のまま移動・衝突・追跡のみ無害化。重トポロジーを維持したままクレーム **100 回**成功・10800 tick 完走 | 200 / accepted |
| **B-rejected** | 同上で **101 回目のクレームが `MAX_VERIFIED_CLAIMS` により早期拒否** | 200 / rejected(`MAX_VERIFIED_CLAIMS (100) exceeded`、1467 tick で打ち切り) |

### 3.4 計測結果

| 系列 | p99 | mean | min | max | 完走 tick |
| --- | --- | --- | --- | --- | --- |
| A | **1,155.47ms** | 542.03ms | 297.33ms | 1,306.00ms | 10800 |
| B-success | **1,553.45ms** | 1,224.54ms | 1,121.28ms | 1,613.16ms | 10800 |
| B-rejected | **1,731.80ms** | 1,135.10ms | 710.80ms | 1,749.20ms | 1467(早期拒否) |

**判定式**: `p99(A) 1,155.47 + max(1,553.45, 1,731.80) = 2,887.27ms` > 1,000ms → **FAIL**

> 実行ログ(`ranking-cpu-local-run.log`)の末尾には
> `p99(A)=1155.54 + max(...)=1681.7 = 2837.24ms` と出ている。
> これは**ログが実行中のストリーミング集計値**、JSON が**全 100 件を確定後に再計算した値**
> という差である。**JSON 側(2,887.27ms)を正**とする。

### 3.5 参考値(妥当性確認用)

実プレイ型フィクスチャの最良値: **ステージ2 / クレーム 31 回 / 8,843 tick**。
合成フィクスチャが実プレイより明確に重い側にあることの確認用。

## 4. この数値の読み方(重要)

計測値は **ローカル wall-clock であって、Cloudflare が課金・制限する CPU 時間ではない**。
両者は次の点で乖離する:

1. **wall-clock ⊃ CPU 時間** — I/O 待ち・GC・ローカル D1(SQLite)アクセス・
   Miniflare のオーバーヘッドを含む。実 CPU 時間はこれより**小さい**。
2. **ローカル workerd ≠ 本番 workerd** — 本番エッジは実行環境もハードウェアも異なる。
3. タスク1の実測(実 Cloudflare 上)では A の p99 が **366ms** と、
   ローカル wall-clock(1,155ms)の **1/3 程度**だった。
   打ち切り込みの値なので直接比較はできないが、
   **ローカル wall-clock が実 CPU 時間を大きく上振れさせている**傍証にはなる。

したがって 1,000ms 判定の FAIL は
**「Paid でも不成立」ではなく「ローカル代理計測では判定式を満たせなかった」**と読むべきである。

- **Free**: 10ms 上限に対して桁が違う。**確実に不成立**(タスク1で確定済み)。
- **Paid**: 含まれる月 3,000万 CPU-ms に対し、後述の投稿頻度なら**余裕がある**見込み。

**Paid の正確な条件**(誤記載しないこと):
Paid は「月$5固定」ではなく **「最低月額 $5 から」**。Workers Paid に Pages Functions も含まれ、
**月 3,000万 CPU-ms** を含む。HTTP リクエストの CPU 上限は既定 30 秒・最大 5 分まで設定可能。

> **本番デプロイ前に必ず再確認すること**: 上記のとおりローカル値は代理値なので、
> Paid 契約後の preview 環境で**実 CPU 時間**(`wrangler tail` / ダッシュボードの
> CPU time メトリクス)を計測し直し、`wrangler.toml` の `[limits] cpu_ms` を
> 実測 p99 の 2 倍程度に再調整すること。

## 5. 投稿頻度の見積り

**これは実測ではなく推測である。** 現時点で本番稼働しておらず、実績値が存在しないため。

前提:

- qixxx は個人開発のブラウザゲームで、宣伝は作者の X 投稿が中心
- ランキングは**上位10件のみ保持**、投稿は**暫定圏内のプレイヤーのみ**に提示される
  (圏外のプレイヤーには名前入力欄すら出ない)
- 1プレイは実質3分固定

見積り:

| 項目 | 見積り | 根拠 |
| --- | --- | --- |
| POST /api/scores | **1日あたり一桁〜数十件** | 上記前提からの推測 |
| ピーク | 公開直後・X で言及された直後に**数百件/日**の可能性 | 同種個人ゲームの一般的傾向からの推測 |

月 3,000万 CPU-ms に対する試算(**保守的に**ローカル wall-clock 1リクエスト ≒ 1,500ms を
そのまま CPU 時間とみなした場合):

- 100 件/日 × 30 日 × 1,500ms = **450万 CPU-ms**(含有分の約 15%)
- 実 CPU 時間はこれより小さいはずなので、さらに余裕がある

→ 想定される投稿頻度では **Paid の含有分に十分収まる**見込み。
ただし上記のとおり**投稿頻度・CPU 時間ともに推測**であり、
本番稼働後に実績で置き換えること。

**denial-of-wallet 対策**は投稿頻度の見積りとは独立に必要:
`[limits] cpu_ms`(暴走の頭打ち)と KV レート制限(`functions/_lib/ranking/rateLimit.ts`)の
両方で二重に抑える。

## 6. 生データ

[`docs/measurements/`](./measurements/) に以下を置いている。

| ファイル | 内容 |
| --- | --- |
| `ranking-cpu-local-A.json` | 系列A: 計測100件の `wallTimesMs` 全数 + 統計 + HTTP ステータス/accepted 値 |
| `ranking-cpu-local-Bsuccess.json` | 系列B-success: 同上 |
| `ranking-cpu-local-Brejected.json` | 系列B-rejected: 同上(+ `rejectionReasons`) |
| `ranking-cpu-local-summary.json` | 3系列の p99 と判定式の結果 |
| `ranking-cpu-local-run.log` | 実行時のタイムスタンプ付きログ(§3.4 の注記も参照) |

各 JSON は `wallTimesMs` に**間引きなしの計測100件**を保持しているので、
p99 以外の分位点も再計算できる。

計測に使ったハーネス自体(`spike-tmp/`)は**本番成果物に含めない**方針のため
リポジトリには入れていない。計測を再現する場合は本ファイルの §3.2 / §3.3 の
方法論とフィクスチャ定義に従って組み直すこと
(フィクスチャ生成は「実 `Game.update()` 経由でクレームを起こす」ことが必須要件)。
