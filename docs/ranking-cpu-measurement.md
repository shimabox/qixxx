# スコアランキング: CPU 計測記録と投稿頻度見積り

スコアランキング機能(`POST /api/scores` のサーバー側リプレイ検証)の CPU コストの計測記録。
**タスク7の停止ポイントの判断材料**としてここに残す。

生データ・ハーネスは [`docs/measurements/`](./measurements/) にある(§6)。

> ## この文書の位置づけ(先に読むこと)
>
> 現行計測の正式名称は **「ローカル in-process wall-clock ベンチマーク」** である。
> 何を決められて何を決められないかを最初にはっきりさせておく。
>
> | 問い | どの計測で決まるか | 現状 |
> | --- | --- | --- |
> | Free 枠で成立するか | **タスク1の実 Cloudflare 計測**(§2) | **不成立で確定済み**(`exceededCpu` 多発) |
> | 実装のどこが CPU を食うか / 変更で悪化していないか | **ローカル in-process wall-clock ベンチマーク**(§4) | 現行の基準値 |
> | Paid 枠で成立するか | **Paid preview の実 CPU 時間**(未実施) | **未確定** |
> | `cpu_ms` の最終値 | **Paid preview の実 CPU 時間**(未実施) | **暫定値のみ**(§4.8) |
>
> **ローカルベンチマークの役割は「実装の CPU 支配部分を再現可能に比較するローカル基準」**
> — 回帰の検出と相対比較のための物差しであって、課金・上限の根拠ではない。
> したがって:
>
> - **この結果で `cpu_ms` を確定しない。** 現在の値は暫定値である。
> - **この結果で Paid 成立/不成立を確定しない。**
> - Free 不成立の根拠は**この計測ではなく**タスク1の実 Cloudflare 計測である。
>
> 理由は測っている量が違うことにある: これは Node プロセス内の wall-clock であり、
> Cloudflare が課金・制限する CPU 時間ではない。実行環境(Apple M1 / Node)も
> 本番エッジの workerd とは別物で、**KV と D1 はインメモリのモック**なので
> その I/O 時間も含まれない(§4.1・§4.5)。

## 0. 計測の来歴(重要 — 古い数値は無効)

このファイルには **4 世代の計測**が載っている(うち2つは無効)。

| 世代 | 何を測ったか | 状態 |
| --- | --- | --- |
| **タスク1**(実 Cloudflare) | デプロイした一時 Worker の**実 CPU 時間** | **有効**(Free 不成立の根拠) |
| **旧ローカル計測**(HTTP wall-clock) | `wrangler pages dev` への HTTP レイテンシ | **❌ 無効。並列実行で汚染**(§3) |
| **検証コア直接計測** | `simulateReplayFromRle()` の実行時間 | **❌ 無効。フィクスチャA が 715 tick で死亡**(§3.2)。下界の参考値としてのみ |
| **ローカル in-process wall-clock ベンチマーク**(現行) | `onRequestPost()` を**丸ごと**プロセス内実行した wall-clock | **有効**(ローカル基準。§4)。ただし Paid 成立と `cpu_ms` の確定には使わない |

無効とした計測とその理由、それらを消さずに残す理由は §3 に書く。

## 1. 結論(先に要点)

| 判定 | 結果 | 根拠 |
| --- | --- | --- |
| Free 枠(10ms CPU/リクエスト)で成立するか | **不成立(確定)** | タスク1の実 Cloudflare 計測(§2) |
| 判定式 `p99(A) + max(p99(B-success), p99(B-rejected)) ≤ 1,000ms` | **FAIL(1,529.92ms)** | ローカルベンチマーク(§4) |
| 現実的なプレイの1リクエスト総コスト | **p99 46.61ms**(合成最大負荷とは2桁違う) | ローカルベンチマーク(§4.4) |
| **Paid 枠で成立するか** | **未確定** | Paid preview の実 CPU 時間で判断する(§4.8) |
| **`cpu_ms` の最終値** | **未確定**(現在は暫定 4000) | 同上 |

判定式は**不合格**。ただしこれは「Paid でも成立しない」という意味ではない。理由は2つある:

1. 判定式が対象にしているのは**攻撃者が構成しうる最悪ケースの合成フィクスチャ**であり、
   実際のプレイは §4.4 のとおり2桁小さい。
2. そもそもこの数値は**ローカル基準であって課金対象の CPU 時間ではない**
   (冒頭の「この文書の位置づけ」)。Paid の可否はこの表では決まらない。

§5 の投稿頻度試算は「Paid ならおそらく余裕がある」ことの**目安**であって、
成立の確定ではない。

## 2. タスク1: Free 枠判定(実施済み・確定事実・有効)

実 Cloudflare 上に一時 Worker をデプロイし、**Cloudflare 自身の `cpuTime` メトリクス**を
`wrangler tail` で読んで計測した。

- フィクスチャA: **p99 = 366ms**
- フィクスチャB-success: **p99 = 477ms**
- 多数のリクエストが **10ms の CPU 上限で強制終了(`exceededCpu`)**

この計測で確定したのは **「Free 枠の 10ms/リクエストでは成立しない」ことのみ**。
打ち切りを含む計測なので「完全実行なら何 ms か」は未確定であり、
**合算値 843ms を完全実行時間として扱ってはならない**。

→ **CPU ゲート不合格(Free 前提)を正式記録する。**

## 3. 無効とした計測(経緯の記録)

### 3.1 旧ローカル HTTP 計測 — ❌ 無効(並列実行で汚染)

> **この節の数値は判断に使ってはならない。**
> 経緯の記録として残すが、**撤回済み**である。

かつてここには次の数値が「タスク6の完全実行再計測」として載っていた:

| 系列 | 記載されていた p99 |
| --- | --- |
| A | 1,155.47ms |
| B-success | 1,553.45ms |
| B-rejected | 1,731.80ms |
| 合算 | 2,887.27ms |

#### 無効とした理由

1. **並列実行による汚染。** 「直列・並列なし」と記載していたが、
   進捗ファイル `ranking-cpu-local-run.log` の元になった
   `measureLocal.progress.txt` を確認すると、**同じ計測スクリプトが3プロセス同時に走っていた**。
   `[A] 100/100 done` が3回、それぞれ異なる p99(1162.45 / 1155.54 / 1155.47)で出力されている。
   3プロセスが同一の wrangler サーバーを叩き、互いに CPU を奪い合っていた。
2. **ログと JSON が別実行の成果物。** 以前ここには
   「ログはストリーミング集計、JSON は再計算」という説明を書いていたが、**これは誤りだった**。
   ログの `p99=1155.54`(08:01:18)と JSON の `1155.47`(08:01:29)は
   **別プロセスの出力**である。整合しない2つの成果物を1つの計測として提示していた。
3. **再現不能。** この計測は `POST /api/_cpu-spike` という
   ベンチ専用エンドポイントに依存していた。当該エンドポイントは
   「10800 tick の再シミュレーションを外部から起動できる高負荷エンドポイントを
   本番構成に残さない」という要件により**成果物から削除済み**である。
   つまり当時のハーネスはもう動かせない。

#### 残す理由

削除すると「一度この数値で判断しかけた」という経緯が消える。
`wrangler.toml` の `cpu_ms` も一時この数値(2,887 × 2 ≒ 6000)で設定していた。
生データ(`ranking-cpu-local-*.json` / `ranking-cpu-local-run.log`)も
**無効の証拠として**そのまま置いてある。

---

### 3.2 検証コア直接計測 — ❌ 無効(フィクスチャA が完走していない)

一度は次の数値を「クリーンな再計測」として載せていた:

| 系列 | p99 |
| --- | --- |
| A | 41.51ms |
| B-success | 1,563.73ms |
| B-rejected | 2,311.17ms |
| 合算 | 2,352.68ms |

#### 無効とした理由

1. **フィクスチャA が受け入れ基準を満たしていなかった。** 生ログに
   `ok ticks=715 claims=0` と残っている — A のリプレイは **715 tick で
   ライフ切れ**しており、「最大敵負荷で 10800 tick 完走」という定義の
   フィクスチャではなかった。その 715 tick 分の p99(41.51ms)を
   A として提示していた。
   **整合性の機械検証を書いておきながら、フィクスチャ自身の受け入れ基準を
   検証項目に入れていなかった**のが直接の原因である(pid・交錯・
   ログとJSONの一致は見ていたが、tick 数を見ていなかった)。
2. **本番 POST の全経路ではなかった。** `simulateReplayFromRle()` を
   直接呼んでおり、ハッシュ計算・D1・レスポンス生成を含まない**下界**だった。
   依頼書の要求は「RLE 検証展開からレスポンス生成まで本番 POST と同一経路」である。

#### 残す理由

§3.1 と同じ。生データ(`verify-cpu-*`)とハーネス
(`measure-verify-cpu.ts`)もそのまま置いてある。
**検証コアだけの下界**としては今も有効な参考値であり、
§4 の全経路計測と突き合わせると「1リクエストのうちどこまでが
再シミュレーションか」が読める。

## 4. ローカル in-process wall-clock ベンチマーク(現行・有効)

### 4.1 何を測っているか

**本番ハンドラ `onRequestPost()`(`functions/api/scores.ts`)そのもの**を、
実際の `Request` を作ってプロセス内で丸ごと実行した時間。含まれるもの:

Origin / Content-Type 検査 → ストリーミング body 読み取り → シード検証 →
base64 デコード → **`verifyReplay()` の RLE 検証つき再シミュレーション** →
Web Crypto による `replay_hash` 計算 → D1 batch → JSON レスポンス生成。

これが依頼書の言う「RLE 検証展開からレスポンス生成まで、本番 POST と同じ経路」である。

**HTTP は経由しない**(ハンドラ直接駆動)。理由:

1. **ベンチ専用ルートを成果物に足さないため。** 旧スパイクの
   `/api/_cpu-spike` は「10800 tick の再シミュレーションを外部から起動できる
   高負荷エンドポイントを本番に残さない」という要件で削除済みであり、復活させない。
2. ローカル `wrangler pages dev` の wall-clock には、キューイング・Miniflare の
   オーバーヘッド・ソケット処理が乗る。**その雑音が §3.1 の計測を壊した当のもの**で、
   しかもどれも Cloudflare が課金する CPU 時間ではない。
3. サーバーもポートもアカウントも要らず、再現できる。

**D1 と KV はインメモリのモック**である。両者の実コストは CPU ではなく I/O であり、
モックなら実行が決定的になる(SQL の prepare / bind は本番同様に実行される)。
→ 得られる値は **DB・KV の I/O 時間を含まない、1リクエストあたりのローカル wall-clock**。
これは冒頭の「この文書の位置づけ」で述べた役割分離の一部である:
再現可能な**ローカル基準**としては I/O のばらつきを排除できて望ましいが、
**本番の1リクエストの実コストそのものではない**ので、
`cpu_ms` や Paid 成立の確定には使わない。

最大負荷フィクスチャは本番が決して作れない敵数・ライフを必要とするため、
**ベンチフックで注入**している。このフックが遠隔から armed になり得ない理由は
§4.7 に書く。

### 4.2 実行環境と方法論

| 項目 | 値 |
| --- | --- |
| マシン | Apple M1 / 8 コア |
| Node.js | v20.19.5 |
| 実行形態 | **単一プロセス・単一スレッド・完全直列**(多重起動はロックファイルで拒否) |
| 各系列 | ウォームアップ 10 + 計測 100、p99 は nearest-rank 法 |
| クレーム生成 | **実 `Game.update()` 経由**(field 直接書き換えなし) |
| フィクスチャ受け入れ | ハーネスが**起動時に検証して満たさなければ throw**(A/B-success は 10800 tick 完走、claims 100/101) |
| 応答の検証 | **全リクエスト(ウォームアップ10+計測100)を1件ずつアサート**し、1件でも外れたら計測全体を即座に異常終了(§4.3) |

多重起動防止は旧計測の失敗を繰り返さないための措置:
ハーネスは `.measure-verify-cpu.lock` を取り、既にあれば**起動を拒否**する。
進捗ログには pid を刻む。

### 4.3 計測結果(2026-08-17)

| 系列 | 内容 | 期待条件(全件アサート) | p99 | mean | min | max |
| --- | --- | --- | --- | --- | --- | --- |
| **A** | 最大敵負荷(ステージ10相当・Wisp 10・Ember 10 が実際に移動)・**10800 tick 完走**(TIME UP) | 200 / accepted / `durationTicks=10800` | **251.49ms** | 177.06ms | 125.90ms | 312.82ms |
| **B-success** | 最大クレーム負荷・重トポロジー・100 クレーム・**10800 tick 完走** | 200 / accepted / `durationTicks=10800` | **1,278.43ms** | 1,112.43ms | 1,033.38ms | 1,608.23ms |
| **B-rejected** | 101 回目のクレームで `MAX_VERIFIED_CLAIMS` 早期拒否 | **422** / `accepted=false` / `error=max-verified-claims-exceeded` | **1,169.19ms** | 1,043.95ms | 971.71ms | 1,228.92ms |
| **R(参考)** | 現実的なステージ1のラン(3,581 tick)。**ベンチフックなしの素の本番経路** | 200 / accepted / `durationTicks=3581` | **46.61ms** | 16.63ms | 7.67ms | 65.54ms |

**判定式**: `251.49 + max(1,278.43, 1,169.19) = 1,529.92ms` > 1,000ms → **FAIL**

期待条件は**記録するだけでなくリクエスト毎にアサート**しており、
1件でも外れた時点でハーネスが例外を投げて計測全体を中断する(成果物も出力されない)。
各系列 **110 件(ウォームアップ10 + 計測100)すべてが期待条件に一致**した。

> この「毎リクエストのアサート」は Sol round 7 の指摘で追加した。
> それ以前のハーネスは `status` / `accepted` / `durationTicks` を
> **記録するだけ**で、`expectTicks` フィールドに至っては宣言されたまま
> 一度も参照されていなかった — つまり誤った tick 数や拒否応答が返っていても
> p99 と最終判定がそのまま生成される状態だった。§3.2 のフィクスチャA 事故
> (715 tick)を二度と静かに通さないための措置である。
> アサートが実際に効くことは、A の期待 tick 数をわざと 9999 にして
> **1件目のウォームアップで異常終了し、成果物が1つも生成されない**ことを
> 確認して検証した。

### 4.4 分かったこと

- **A は §3.2 の 41.51ms → 251.49ms。** §3.2 の A は 715 tick で死んでいたので、
  同じ「最大敵負荷」でも中身が別物だった。10800 tick を完走させると 6 倍になる。
- **支配的コストはやはりクレーム処理。** 敵最大で完走しても 251ms、
  クレーム最大だと 1,270ms 超。`MAX_VERIFIED_CLAIMS` が
  重要なプロトコルパラメータである理由がこの差に出ている。
- **B-rejected < B-success**(1,169.19 vs 1,278.43)。
  早期拒否が実際に効いていて、101 回目で打ち切る方が 100 回完走より安い。
  §3.2 では逆転していたが、あれは系列内ドリフト込みの値だった。
- **現実的なプレイは1リクエスト 46.61ms**。合成最悪ケースとは2桁違う。
  判定式が見ているのは「攻撃者が投げうる最悪の入力」であって通常運用のコストではない。

### 4.5 既知の計測上の注意

- **系列内ドリフトは今回小さい。** 最初の20件と最後の20件の平均比は
  A 1.12 / B-success 1.02 / B-rejected 0.99 / R 1.14。
  §3.2 の B-rejected に出ていた 1.42 倍のような大きなドリフトはない
  (A と R は絶対値が小さく、ばらつきの比が出やすいだけである)。
- **D1 / KV はモック**なので、その I/O 時間は含まれない(§4.1)。
- **これは実 CPU 時間ではない。** Node プロセス内の wall-clock であり、
  本番エッジのハードウェア・ランタイム(workerd)とも異なる。
  タスク1の実測(実 Cloudflare)では A の p99 が 366ms(打ち切り込み)だった。
- 以上より、この節の数値は**ローカル基準**として読むこと。
  Paid 成立と `cpu_ms` の確定は §4.8 の手順で行う(冒頭の「この文書の位置づけ」)。

### 4.6 Paid の正確な条件(誤記載しないこと)

Paid は「月$5固定」ではなく **「最低月額 $5 から」**。Workers Paid に Pages Functions も含まれ、
**月 3,000万 CPU-ms** を含む。HTTP リクエストの CPU 上限は既定 30 秒・最大 5 分まで設定可能。

> **Paid 成立の判断と `cpu_ms` の確定は、この文書のローカル計測では行わない。**
> 手順は §4.8 を参照。

### 4.7 ベンチフックの隔離(本番から到達不能であること)

最大負荷フィクスチャの注入には `functions/_lib/ranking/benchHooks.ts` を使う。
本番から armed になり得ない理由は**2重**で、2つ目は構造的なものである:

1. `BENCH_HOOKS` が正確に `'enabled'` であること。`wrangler.toml` は
   この binding を定義していない。
2. `BENCH_GAME_FACTORY` が **実際の JavaScript 関数**として `env` に載っていること。
   Cloudflare の binding は文字列・KV/D1/R2 ハンドル等であり、
   **関数を env に届けられる binding 型も、リクエストボディ・ヘッダ・
   クエリ文字列も存在しない**。したがってフラグの側を仮に操作できたとしても、
   `env` を組み立てるのと同一プロセスのコード(= ハーネス)以外からは armed にできない。

これは `SessionOptions.gameFactory` に既に適用されている隔離規則と同じ流儀である。

検証は `functions/_lib/ranking/benchHooks.test.ts` が自動で行う:
production 形状の env・フラグのみ・関数でない値・フラグなしの関数がいずれも
`undefined` を返すこと、`wrangler.toml` が両 binding を定義していないこと、
そして **`BENCH_HOOKS` を含むファイルがモジュール本体・そのテスト・
ハーネスの3つだけ**であること(他のリクエスト経路への波及防止)。

### 4.8 Paid 成立と `cpu_ms` の確定手順(未実施)

**ここが最終判断の場所である。** §4 のローカルベンチマークは基準値であって、
この手順の代わりにはならない。

1. Paid 契約後、**preview 環境**にデプロイする。
2. **実 CPU 時間**を計測する — `wrangler tail` の per-invocation `cpuTime`、
   または Cloudflare ダッシュボードの CPU time メトリクス。
   ローカル wall-clock ではなく、**Cloudflare が課金・制限している値そのもの**を見ること。
3. 同じフィクスチャ構成(A / B-success / B-rejected)と同じ方法論
   (ウォームアップ10 + 計測100、nearest-rank p99)で p99 を出す。
   ベンチフックは本番から到達不能なので(§4.7)、preview で最大負荷フィクスチャを
   使う場合はハーネスと同様に**プロセス内から**注入するか、
   現実的なフィクスチャ(系列 R 相当)での計測に切り替えて判断すること。
4. その**実 CPU 時間の p99** をもとに:
   - **Paid 成立/不成立を判断する**(月 3,000万 CPU-ms の含有分に対する試算)。
   - **`cpu_ms` を確定する**(実測 p99 の 2 倍程度)。
     現在の `4000` は §4.3 のローカル基準から置いた**暫定値**にすぎない。
5. 判断結果をこの文書に追記し、`wrangler.toml` のコメントを暫定表記から改めること。

参考として、ローカル基準と実 Cloudflare 計測の乖離の目安:
タスク1(実 Cloudflare、打ち切り込み)の A は p99 366ms、
ローカル基準の A は 251.49ms。測っている量も条件も違うので
換算係数として使えるものではないが、**桁が同じであることの確認**にはなる。

## 5. 投稿頻度の見積り

**これは実測ではなく推測である。** 本番稼働しておらず実績値が存在しない。

前提:

- 個人開発のブラウザゲームで、宣伝は作者の X 投稿が中心
- ランキングは**上位10件のみ保持**、投稿は**暫定圏内のプレイヤーのみ**に提示される
  (圏外なら名前入力欄すら出ない)
- 1プレイは実質3分固定

| 項目 | 見積り | 根拠 |
| --- | --- | --- |
| POST /api/scores | **1日あたり一桁〜数十件** | 上記前提からの推測 |
| ピーク | 公開直後・X 言及直後に**数百件/日**の可能性 | 同種個人ゲームの一般的傾向からの推測 |

月 3,000万 CPU-ms に対する**粗い目安**(1件あたりの時間は
ローカル基準の wall-clock を CPU 時間の代わりに置いた試算であり、実測ではない):

| シナリオ | 1件あたり(ローカル基準) | 100件/日 × 30日 | 含有分に対する割合 |
| --- | --- | --- | --- |
| 現実的なラン | 46.61ms | 約 14万 | **約 0.5%** |
| 合成最悪ケースばかりが来た場合 | 1,529.92ms | 約 459万 | 約 15% |

現実的な投稿しか来ないなら含有分の約0.5%、
仮に全リクエストが最悪ケースの合成入力でも約15%に収まる計算になる。

→ **「Paid ならおそらく余裕がある」ことの目安**としては使える。
ただし**これは Paid 成立の判断ではない**:
投稿頻度は推測であり、1件あたりの時間もローカル基準の代理値だからである。
成立の可否は §4.8 のとおり **Paid preview の実 CPU 時間**で判断し、
本番稼働後は投稿頻度も実績で置き換えること。

**denial-of-wallet 対策**は投稿頻度の見積りとは独立に必要:
`[limits] cpu_ms`(暴走の頭打ち)と KV レート制限
(`functions/_lib/ranking/rateLimit.ts`、1 IP / 1時間 / 10件)の両方で二重に抑える。


整合性は次のとおり機械的に確認済み(2026-08-17 の実行):

- 進捗ファイル中の pid は1つのみ / タイムスタンプは単調非減少

- **フィクスチャA が全100リクエストで `durationTicks=10800` / status 200 / accepted**
  (§3.2 で見落とした受け入れ基準。生成側でも `ticks=10800` かつ `reason=time` を確認)
