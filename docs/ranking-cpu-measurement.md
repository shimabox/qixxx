# スコアランキング: CPU 計測記録と投稿頻度見積り

スコアランキング機能(`POST /api/scores` のサーバー側リプレイ検証)の CPU コストの計測記録。
**タスク7の停止ポイントで Paid / Free を判断するための材料**としてここに残す。

生データ・ハーネスは [`docs/measurements/`](./measurements/) にある(§6)。

---

## 0. 計測の来歴(重要 — 古い数値は無効)

このファイルには **2 世代の計測**が載っている。

| 世代 | 何を測ったか | 状態 |
| --- | --- | --- |
| **タスク1**(実 Cloudflare) | デプロイした一時 Worker の**実 CPU 時間** | **有効**(Free 不成立の根拠) |
| **旧ローカル計測**(HTTP wall-clock) | `wrangler pages dev` への HTTP レイテンシ | **❌ 無効。手順に不備**(§3) |
| **新ローカル計測**(検証コア直接) | 検証コアの**プロセス内実行時間** | **有効**(現行の判断材料。§4) |

旧ローカル計測を無効とした理由と、それを消さずに残す理由は §3 に書く。

## 1. 結論(先に要点)

| 判定 | 結果 |
| --- | --- |
| Free 枠(10ms CPU/リクエスト)で成立するか | **不成立(確定)** |
| 判定式 `p99(A) + max(p99(B-success), p99(B-rejected)) ≤ 1,000ms` | **FAIL(2,352.68ms)** |
| Paid 枠で成立するか | **成立する見込み**(§5 の投稿頻度試算) |
| 現実的なプレイの検証コスト | **p99 96.41ms**(合成最大負荷とは2桁違う。§4.4) |

判定式は**不合格**。ただしこれは「Paid でも成立しない」という意味ではない。
判定式が対象にしているのは**攻撃者が構成しうる最悪ケースの合成フィクスチャ**であり、
実際のプレイは §4.4 のとおり2桁小さい。§4.5 の読み方を必ず併せて参照すること。

---

## 2. タスク1: Free 枠判定(実施済み・確定事実・有効)

実 Cloudflare 上に一時 Worker をデプロイし、**Cloudflare 自身の `cpuTime` メトリクス**を
`wrangler tail` で読んで計測した。

- フィクスチャA: **p99 = 366ms**
- フィクスチャB-success: **p99 = 477ms**
- 多数のリクエストが **10ms の CPU 上限で強制終了(`exceededCpu`)**

この計測で確定したのは **「Free 枠の 10ms/リクエストでは成立しない」ことのみ**。
打ち切りを含む計測なので「完全実行なら何 ms か」は未確定であり、
**合算値 843ms を完全実行時間として扱ってはならない**。

→ **CPU ゲート不合格(Free 前提)を正式記録する。**

## 3. 旧ローカル計測 — ❌ 無効(計測手順に不備)

> **この節の数値は判断に使ってはならない。**
> 経緯の記録として残すが、**撤回済み**である。

かつてここには次の数値が「タスク6の完全実行再計測」として載っていた:

| 系列 | 記載されていた p99 |
| --- | --- |
| A | 1,155.47ms |
| B-success | 1,553.45ms |
| B-rejected | 1,731.80ms |
| 合算 | 2,887.27ms |

### 無効とした理由

1. **並列実行による汚染。** 「直列・並列なし」と記載していたが、
   進捗ファイル `ranking-cpu-local-run.log` の元になった
   `measureLocal.progress.txt` を確認すると、**同じ計測スクリプトが3プロセス同時に走っていた**。
   `[A] 100/100 done` が3回、それぞれ異なる p99(1162.45 / 1155.54 / 1155.47)で出力されている。
   3プロセスが同一の wrangler サーバーを叩き、互いに CPU を奪い合っていた。
2. **ログと JSON が別実行の成果物。** 以前ここには
   「ログはストリーミング集計、JSON は再計算」という説明を書いていたが、**これは誤りだった**。
   ログの `p99=1155.54`(08:01:18)と JSON の `1155.47`(08:01:29)は
   **別プロセスの出力**である。整合しない2つの成果物を1つの計測として提示していた。
3. **再現不能。** この計測は `POST /api/_cpu-spike` という
   ベンチ専用エンドポイントに依存していた。当該エンドポイントは
   「10800 tick の再シミュレーションを外部から起動できる高負荷エンドポイントを
   本番構成に残さない」という要件により**成果物から削除済み**である。
   つまり当時のハーネスはもう動かせない。

### 残す理由

削除すると「一度この数値で判断しかけた」という経緯が消える。
`wrangler.toml` の `cpu_ms` も一時この数値(2,887 × 2 ≒ 6000)で設定していた。
生データ(`ranking-cpu-local-*.json` / `ranking-cpu-local-run.log`)も
**無効の証拠として**そのまま置いてある。

## 4. 新ローカル計測(現行・有効)

### 4.1 何を測っているか

**検証コア(リプレイ再シミュレーション)のプロセス内実行時間**。
`POST /api/scores` のコストを支配するのはこの再シミュレーションである。

HTTP を経由**しない**。理由は2つ:

1. 旧計測が使っていたベンチ専用エンドポイントは**意図的に削除済み**で、復活させない。
2. ローカル `wrangler pages dev` の wall-clock には、キューイング・Miniflare の
   オーバーヘッド・ローカル SQLite アクセス・GC が乗る。
   **その雑音こそが旧計測を信用できなくした当のもの**であり、
   しかもそのどれも Cloudflare が課金する CPU 時間ではない。

実 POST で代替することもできない: レート制限が **1 IP あたり 1 時間 10 リクエスト**であり、
かつ最大敵数フィクスチャは**ベンチ用 `gameFactory` 経由でしか構成できない**
(本番からは到達不能に保つ必要がある)。

→ したがってこれは**支配的コストの、再現可能でクリーンな計測**であって、
エンドツーエンドのリクエスト計測ではない。
ハッシュ計算・D1・レスポンス生成を含まないので、**リクエスト CPU の下限**である。

### 4.2 実行環境と方法論

| 項目 | 値 |
| --- | --- |
| マシン | Apple M1 / 8 コア |
| Node.js | v20.19.5 |
| 実行形態 | **単一プロセス・単一スレッド・完全直列**(多重起動はロックファイルで拒否) |
| 各系列 | ウォームアップ 10 + 計測 100、p99 は nearest-rank 法 |
| クレーム生成 | **実 `Game.update()` 経由**(field 直接書き換えなし) |

多重起動防止は旧計測の失敗を繰り返さないための措置:
ハーネスは `.measure-verify-cpu.lock` を取り、既にあれば**起動を拒否**する。
進捗ログには pid を刻む。

### 4.3 計測結果(2026-08-17)

| 系列 | 内容 | p99 | mean | min | max |
| --- | --- | --- | --- | --- | --- |
| **A** | 最大敵負荷(ステージ10相当・Wisp 10・Ember 10 が実際に移動)・10800 tick | **41.51ms** | 15.36ms | 7.65ms | 47.54ms |
| **B-success** | 最大クレーム負荷・重トポロジー・100 クレーム・10800 tick | **1,563.73ms** | 1,363.81ms | 1,265.48ms | 1,624.69ms |
| **B-rejected** | 101 回目のクレームで `MAX_VERIFIED_CLAIMS` 早期拒否(1467 tick) | **2,311.17ms** | 1,683.13ms | 1,232.25ms | 2,552.86ms |
| **R(参考)** | 現実的なステージ1のラン。**本物の `verifyReplay()`**(gameFactory なし) | **96.41ms** | 33.01ms | 12.77ms | 101.33ms |

**判定式**: `41.51 + max(1,563.73, 2,311.17) = 2,352.68ms` > 1,000ms → **FAIL**

### 4.4 分かったこと

- **A は旧計測の 1,155ms → 41.5ms。** 旧 A の数値は**ほぼ全部が HTTP と
  Miniflare のオーバーヘッドと並列汚染**であって、シミュレーションのコストではなかった。
- **支配的コストはクレーム処理**であって敵数ではない。敵最大でも 41.5ms、
  クレーム最大だと 1,500ms 超。`MAX_VERIFIED_CLAIMS` が
  重要なプロトコルパラメータである理由がこの数字に出ている。
- **現実的なプレイは p99 96.41ms**。合成最悪ケースとは2桁違う。
  判定式が見ているのは「攻撃者が投げうる最悪の入力」であり、通常運用のコストではない。

### 4.5 既知の計測上の注意

- **B-rejected に系列内ドリフトがある。** 最初の20件平均 1,317.7ms に対し
  最後の20件平均 1,870.5ms(**1.42倍**)。
  約25分の連続全力実行による M1 のサーマルスロットリングと見られる
  (他系列にドリフトはなく、R はむしろ JIT ウォームアップで改善している)。
  したがって B-rejected の p99 は**過大評価側**であり、
  安全上限を決める用途では保守的な方向なのでそのまま採用している。
- **これは実 CPU 時間ではない。** プロセス内 wall-clock であり、
  本番エッジのハードウェア・ランタイムとも異なる。
  タスク1の実測(実 Cloudflare)では A の p99 が 366ms(打ち切り込み)だった。

### 4.6 Paid の正確な条件(誤記載しないこと)

Paid は「月$5固定」ではなく **「最低月額 $5 から」**。Workers Paid に Pages Functions も含まれ、
**月 3,000万 CPU-ms** を含む。HTTP リクエストの CPU 上限は既定 30 秒・最大 5 分まで設定可能。

> **本番デプロイ前に必ず再確認すること**: 上記のとおりこれは代理値である。
> Paid 契約後の preview 環境で**実 CPU 時間**(`wrangler tail` /
> ダッシュボードの CPU time メトリクス)を測り直し、
> `wrangler.toml` の `[limits] cpu_ms` を実測 p99 の 2 倍程度に再調整すること。

## 5. 投稿頻度の見積り

**これは実測ではなく推測である。** 本番稼働しておらず実績値が存在しない。

前提:

- 個人開発のブラウザゲームで、宣伝は作者の X 投稿が中心
- ランキングは**上位10件のみ保持**、投稿は**暫定圏内のプレイヤーのみ**に提示される
  (圏外なら名前入力欄すら出ない)
- 1プレイは実質3分固定

| 項目 | 見積り | 根拠 |
| --- | --- | --- |
| POST /api/scores | **1日あたり一桁〜数十件** | 上記前提からの推測 |
| ピーク | 公開直後・X 言及直後に**数百件/日**の可能性 | 同種個人ゲームの一般的傾向からの推測 |

月 3,000万 CPU-ms に対する試算:

| シナリオ | 1件あたり | 100件/日 × 30日 | 含有分に対する割合 |
| --- | --- | --- | --- |
| 現実的なラン(実測 p99) | 96.41ms | 約 29万 CPU-ms | **約 1%** |
| 合成最悪ケースばかりが来た場合 | 2,352.68ms | 約 706万 CPU-ms | 約 24% |

現実的な投稿しか来ないなら**含有分の約1%**。
仮に全リクエストが最悪ケースの合成入力だったとしても約24%に収まる。
→ 想定される投稿頻度では **Paid の含有分に十分収まる**見込み。
ただし**投稿頻度・CPU 時間ともに推測**であり、本番稼働後に実績で置き換えること。

**denial-of-wallet 対策**は投稿頻度の見積りとは独立に必要:
`[limits] cpu_ms`(暴走の頭打ち)と KV レート制限
(`functions/_lib/ranking/rateLimit.ts`、1 IP / 1時間 / 10件)の両方で二重に抑える。

## 6. 生データとハーネス

[`docs/measurements/`](./measurements/):

### 現行(有効)

| ファイル | 内容 |
| --- | --- |
| `measure-verify-cpu.ts` | **再現用ハーネス**。フィクスチャ生成から集計まで自己完結 |
| `verify-cpu-<stamp>.progress.txt` | 進捗ログ(pid 付き) |
| `verify-cpu-<stamp>.json` | 全系列の**計測100件の生サンプル**+統計 |
| `verify-cpu-<stamp>-summary.json` | p99 と判定 |

**この3ファイルは同一プロセス・同一実行の成果物**であり、
`<stamp>` が一致するものが1組。再実行するには:

```sh
npx vite-node docs/measurements/measure-verify-cpu.ts
```

整合性は次のとおり機械的に確認済み(2026-08-17 の実行):

- 進捗ファイル中の pid は1つのみ / タイムスタンプは単調非減少
- 各系列の進捗カウンタが `20,40,60,80,100` を**ちょうど1回ずつ**(交錯なし)
- **進捗ログの p99 と JSON の p99 が全系列で一致**
- 各系列のサンプル数がちょうど100 / 合算値が JSON から再計算して一致

### 旧(❌ 無効・§3 参照)

`ranking-cpu-local-A.json` / `-Bsuccess.json` / `-Brejected.json` /
`-summary.json` / `-run.log` — **並列汚染された計測の生データ。判断に使わないこと。**
